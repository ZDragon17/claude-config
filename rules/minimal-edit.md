# 最小化精准编辑规则

代码修改必须精确定位、只改需要改的地方，禁止全量删除后重写。

## 核心原则

**正常人类的修改逻辑**：只修改那个有异议的、需要修改的地方，而不是全量删除后重写整个文件或段落。

## 强制规则

1. **禁止全量删除重写** — 不允许把整个文件/段落内容删掉再重新写一遍
2. **Edit > Write** — 修改已有文件时，优先使用 `Edit`（精确字符串替换）而非 `Write`（全量覆写）
3. **Read 在前** — 修改前必须先 Read 目标文件，精确定位需要改的行号
4. **逐个精准修改** — 多处需要改时，多次 `Edit` 逐个处理，每次只动目标行
5. **改后自检** — 改完用 `git diff` 验证：改动范围刚好覆盖意图，没有多余"意外变更"

## 反模式警示

| 错误做法 | 正确做法 |
|---------|---------|
| 把整个函数/类内容删掉，重新写一份 | 定位到需要改的那几行，用 Edit 精确替换 |
| 用 Write 覆写整个文件 | 多次 Edit 逐个修改点处理 |
| 改动范围超出意图 5 倍行数 | git diff 应该只显示目标修改行 + 必要上下文行 |

## 自查信号

如果一个 `Edit` 的 `old_string` 覆盖了超过 **30 行**，停下来思考：
- 是否真的需要改这么多？
- 能不能拆成多个更小的 Edit？
- 是不是在无意间重写了不需要改的代码？

## Why

全量删除重写有三个致命问题：
1. **diff 不可读** — 看不出实际改了什么，code review 几乎不可能
2. **容易引入意外变更** — 重写过程中可能无意改变原本没想动的逻辑
3. **丢失历史 blame** — 整段被标记为新代码，git blame 追溯失效

这是 AI 常见坏习惯：看起来省事（一次性写完），实际上给 code review 和代码追溯制造了不必要的噪音。

## How to apply

每次修改代码时：
1. Read 文件 → 精确定位目标行
2. Edit(old_string=目标行, new_string=修改后内容)
3. 重复步骤 2 直到所有修改点处理完毕
4. `git diff` → 确认改动范围 = 意图范围
5. 如果 diff 显示改动行数远超预期 → 说明用了全量重写，回退重来
