# 工作流路由详细手册

> 5 合 1 详细版：原 `team-mode-trigger.md` / `autoresearch-trigger.md` / `loop-mode-trigger.md` / `composite-workflow.md` / `orchestration-playbook.md` 已全部并入此处。
> 常驻精简决策表见 `routing-core.md`，本文件是其按需展开的完整手册。
> 边界：人工卡点见 `human-gate.md`；codex 二审是否调用见 `codex-review-policy.md`；自主/确认边界见 `autonomous-judgment.md`。

## 一、顶层决策（按意图选基础栈）

先按**意图**选基础栈，再按**叠加信号**追加节点（第六节）。

| 意图 | 信号词 | 基础栈 |
| --- | --- | --- |
| **探索/调研** | 看看 / 分析 / 调研 / 评估 / 找找 | Explore 或蜂群（多视角并行 read）+ 汇总 |
| **实现/开发** | 实现 / 添加 / 做一个 / 新增 | Plan → 狼群（按模块分工 write）→ 编译/测试 |
| **修 bug** | 修 / 排查 / 根因 / 复现 / 错 / 失败 | debugger → 定位 → 改 → 测试验证 |
| **审查/评估** | 审 / review / 复核 / 评审 / 扫一遍 | 蜂群（多 reviewer 视角并行）+ codex 二审（按需，见 `codex-review-policy.md`） |
| **完整交付** | 做完 / 搞定 / 修完 / 端到端 / ultrawork | ultrawork 全闭环（第五节） |

**关键编排原则**：

1. **不退回单一工具** — 多个工具名/信号位时主动组合，不简化成单选
2. **蜂群 ≠ 狼群** — 读用蜂群，写用狼群（第二节）
3. **autoresearch 永远在外层** — 迭代壳，包住其他栈（第三节）
4. **codex 二审放最末，但是否调用按需判定** — 命中即用时它是最后一道闸，**何时调用以 `codex-review-policy.md` 为准（不是每次都跑）**
5. **UI/功能改动必须真实验证** — 编译过 ≠ 功能可用，见 `real-e2e-testing.md`
6. **复杂栈先复述再开跑** — 一句话「理解为 X→Y→Z，goal=G，metric=M，开跑？」用户答"开"立即执行

## 二、蜂群 vs 狼群（读写区分）

| 用户词 | 机制 | 实操 | 适用 |
| --- | --- | --- | --- |
| **蜂群** | subagents（单层 fanout） | `Agent` 派 N 个 subagent，**结果汇总回我** | 并行 **read / 审查 / 评估 / 调研**（只读为主） |
| **狼群 / 团队 / 派狼** | agents（Team 模式） | 平级 agent 协作、独立决策，**可 write**；是否给每个 agent 开 worktree 隔离按规模定（默认 < 5 文件不开，见 `autoresearch-loop-execution.md` 3a） | 并行 **改代码 / 分模块修复**（write 为主） |

**判断原则**：看 / 审 / 分析 / 评估 / 找问题 → 蜂群；改 / 修 / 写 / 重构 → 狼群；用户明说哪个就用哪个，不擅自换。

**触发关键词**：蜂群「开蜂群 / 蜂群审 / 派蜂」；狼群「开狼群 / 派狼 / 派狼修」；团队「team 模式 / 组个队」；「并行处理 / 同时搞」按是否动写决定蜂群/狼群。

**自主判断触发**（无需关键词，按性质选）：

1. ≥ 3 个独立文件/模块无依赖修改 → 狼群
2. 多维度审查（安全 + 性能 + 测试视角）→ 蜂群
3. 跨层修复（Controller + Service + Mapper 独立）→ 狼群
4. "看看 / 分析 / 调研" + 多个模块 → 蜂群

**自主决策范围**（不反问用户）：选哪种 agent type、几个 teammate、怎么分任务。**铁律：同一文件不能被两个 teammate 同时编辑。**

**Why**：用户用自然界类比 — 蜂群有蜂后统一管控（主代理汇总），狼群是头狼带队但各自独立行动（团队协作）。

## 三、autoresearch 循环触发

**触发规则（两条任一即升级）**：① 「蜂群 / 狼群 / 派狼 / 派蜂」+ 任何「直到 / 循环 / 多几轮 / 反复 / 再扫一轮 / 一直跑」同时出现 → autoresearch 迭代循环;② **明确可量化目标**（调到/压到/降到/提到/达到/做到/修到/控制在 + 数字阈值，或 零报错/全绿/全过/不再复现/0 failures/100%）→ **即使没说"循环"也升 goal-loop**（自动定 `max N 轮`）。开跑后执行步骤见 `autoresearch-loop-execution.md`。**两者都不满足的普通任务**（如"实现X / 优化一下代码"，无可量化目标）**不主动升级**，避免简单任务被套迭代框架烧 token。

**Goal / Metric 自动提取**（从用户原话提取，不让用户写 `--goal --metric`；没 metric 就退化成普通 loop）：

| 用户原话 | goal | metric |
| --- | --- | --- |
| "循环狼群修到测试全绿" | 修测试失败 | 测试 0 failures |
| "反复跑直到这个 bug 不再复现" | 修指定 bug | 复现率 = 0（连续 N 次稳定） |
| "循环蜂群审，直到没扫出新问题" | 代码审查找问题 | 连续 2 轮零新 finding |
| "调到 P95 < 200ms" | 接口性能优化 | P95 < 200ms |
| "修到零编译错误" | 修编译错误 | 编译 exit 0 |

> 触发归属：含循环词的行（"循环狼群修到测试全绿"等）由触发①;**不含循环词但有可量化目标的行（"调到 P95 < 200ms"、"修到零编译错误"）由触发②独立升级**，不必再补"循环"二字。

**复述确认协议**：提取后一句话复述再开跑，不反复确认：

```
理解为：机制=狼群/蜂群，子命令=:fix/:debug/:security/:reason/通用，goal=X，metric=Y，max N 轮。开跑？
```

- 用户答"开 / 行 / 嗯" → 立即跑；改 metric → 改完再跑；**提取不到 metric → 只问 metric 这一个问题，不问别的**。
- **`max N 轮` 必须填具体数字**（默认值见 `routing-core.md` 信号叠加表），不写"若干轮"——这是判停硬闸，到上限仍未收敛就强制停 + 报告让用户拍板，不擅自续命（执行细节见 `autoresearch-loop-execution.md` 第 5b 节）。

**子命令路由**：

| 关键词 | 子命令 |
| --- | --- |
| bug / 排查 / 根因 / 复现 | `:debug` |
| 编译 / 测试 / 失败 / lint / 报错 | `:fix` |
| 安全 / 漏洞 / 红队 / STRIDE / OWASP | `:security` |
| 方案 / 设计 / 打磨 / 精化 | `:reason` |
| 边界 / 场景 / 穷举 | `:scenario` |
| 多视角预分析 | `:predict` |
| 8 阶段交付 / ship | `:ship` |
| 文档 / 学习仓库 | `:learn` |
| 需求 / 假设 / 拷问 | `:probe` |
| 其他可量化目标 | `:autoresearch`（通用） |

## 四、loop 持续监控

**触发关键词**："持续监控 / 一直盯着 / 帮我看着"、"定时检查 / 每隔 X 分钟看一下 / 轮询"、"循环模式 / loop 模式"、"构建好了告诉我 / 部署完了通知我 / 等它跑完"、"盯着 CI / 部署 / 日志"。

**自主判断触发**：用户启动长任务（mvn package / docker build）并关心结果；提到需等待的外部流程（CI / PR review / 部署）；要求周期性做某事。

**自主决策范围**：轮询间隔（构建 2-3m、部署 5m、数据同步 1h）、检查内容与汇报格式、何时建议停止。

**与 autoresearch 的边界**：单纯"盯着 / 等它跑完" → loop；"盯着 + 直到 X 达标" + 可量化 metric → autoresearch（第三节）。

## 五、ultrawork 全闭环

编排：`Team 并行开发 → Loop 持续验证 → 交付（提交/PR）`

1. **Team 并行开发**：按复杂度决定是否开 team（第二节），按文件无冲突划分 teammate。
2. **Loop 持续验证**：编译 / 测试 / 类型检查，发现失败立即修，不等用户问。
3. **自动交付**：全绿后汇总改动 → 输出方案确认（见 `autonomous-judgment.md` 边界判定表）→ 用户确认后 commit / PR。

**触发**："把 XX 做完 / 帮我搞定 / 修完这些"、"做完测试通过了就提 PR"、"ultrawork / ulw / 端到端做完"、给定明确功能需求/bug 列表且期望完整交付。

**不触发**：只问问题 / 要方案 / 做调研；"先改这一个文件"；"先别提交"（跳过交付阶段）。

**人工卡点**：跑到金额/统计/报告（业务对账）、DDL/批量数据（生产变更）、跨仓库契约（DTO/OpenAPI）必须停下等人，见第八节与 `human-gate.md`。

## 六、叠加信号位（基础栈上加节点）

按信号位**叠加**，不互斥：

| 信号词 | 追加节点 |
| --- | --- |
| **直到 / 循环 / 反复 / 多几轮** | 整栈外套 autoresearch 循环（第三节） |
| **codex / 二审 / 复核** | 末尾加 codex review（**是否调用按需判定**，见 `codex-review-policy.md`） |
| **UI / 前端 / 截图 / 看效果** | 末尾用 Playwright MCP 真实打开浏览器验证（见 `real-e2e-testing.md`） |
| **盯 / 持续监控 / 等它跑完** | 整栈外套 loop（第四节） |
| **安全 / 漏洞 / 红队** | 中段加 `:security` 或 `security-reviewer` |
| **性能 / 慢 / P95 / 超时** | 中段加 `performance-engineer` + EXPLAIN（见 `db-perf-cover-index.md`） |
| **方案 / 设计 / 拍板** | 起始加 Plan + AskUserQuestion（见 `autonomous-judgment.md` 边界判定表） |

**典型组合**（参考，不穷举）：

- "循环狼群修 X 直到测试全绿，codex 也要过" → autoresearch(狼群:fix → 测试 → codex review) 直到都过
- "把这个功能做完，UI 要测过" → ultrawork(Plan → 狼群 write → 测试 → Playwright MCP 验证 → codex → commit)
- "循环蜂群审直到没新问题，再派狼群修" → autoresearch(蜂群审) 收敛后 → 狼群:fix → codex
- "排查这个 bug，多几轮直到根因清楚" → autoresearch:debug(debugger → 假设 → 验证 → 推翻 → 再假设)

**Why**：工具价值在组合 — 蜂群×狼群=边改边审，狼群×autoresearch=自动修到达标，autoresearch×codex=异构 metric 防过拟合，ultrawork=全部叠加的顶层封装。

## 七、自学习节点（半自动 skill 沉淀）

**机制详见 `autonomous-judgment.md`「半自动沉淀机制」**（我自主触发时机 + 直接贴草稿 + 用户一句话审 + 落盘）。本节只列触发信号、落盘位置与红线。

**触发式沉淀信号**（任一命中 → 抽草稿贴出来让用户审）：

1. 用户明示「这个套路记下来 / 沉淀一下 / 以后这么干」
2. 连续 ≥ 2 次用同一非平凡解法（同种工具组合 / 调试套路）
3. 复杂任务结束 + 用户说「搞定 / 通过 / 不错」+ 涉及 ≥ 3 个工具组合

**批量复盘触发**：memory 累计 ≥ 5 条未复核 / 同类草稿被多次拒绝 / 同会话连续 ≥ 3 次纠正同一类行为 → 自主扫近期 memory 输出候选规则清单让用户筛。

**落盘位置**：通用工作方式 → `~/.claude/rules/{name}.md`；可复用工作流 → `~/.claude/skills/{name}/SKILL.md`；项目特有经验 → 项目级 memory。

**红线**：用户不需敲任何手动命令（我自己判断）；但**落盘前必须贴草稿让用户审**，避免技能库黑洞污染；不全自动落 skill（Hermes 式技能爆炸会让低质 skill 互相覆盖、下次不知用哪个）。

## 八、与人工卡点的边界

这套自动编排**高于**单工具触发，但**低于** `human-gate.md` 的 3 道强制人工卡点（业务对账 / 生产变更 / 跨仓库契约）。命中卡点关键词（金额 / 统计 / DDL / 批量 DML / DTO / openapi 等）→ 即使 ultrawork / autoresearch 跑到该步也必须停下等人。详见 `human-gate.md`，本文件不重复。

**顶层 Why**：AI 工具栈覆盖开发执行的 80%，剩下 20% 是"AI 不该擅自决定"的领域（业务正确性、生产数据安全、跨系统契约）。极限不是"无死角全自动"，而是"在能自动的地方自动，在该停的地方停"。
