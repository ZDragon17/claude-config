# 用户档案（作者）

跨所有项目通用 — 只沉淀**能力**与**视野**，决定我用什么深度解释、什么颗粒度给方案。
具体项目（路径 / 当前阶段 / 红线）见各项目 memory（`~/.claude/projects/{项目}/memory/`），本档案不收录。

## 能力域（决定能在哪些方向深聊、方案给到多细）

- **后端**：Spring Boot / Java 模块化单体（深度）；数据库性能调优经验丰富（执行计划、覆盖索引、慢查询定位）
- **IoT 协议**：MQTT、Modbus RTU/TCP、RS485 总线（深度），手写过设备协议解析器
- **前端**：Vue 3 + Element Plus（熟练），React Native（学习中）
- **工程化**：容器编排、时序数据库、消息中间件、数据库迁移、鉴权框架等全栈落地经验

## 视野 / 判断取向

- **架构**：偏好「单一信源 + 锚点引用」组织文档；务实主义而非纯理论
- **选型**：工具适配优于堆砌 —— 合适的需求选合适的组件，不硬塞。引入新工具/框架时先列「✅适配 / ❌不适配 / ⚠️边缘」分类表，只在 sweet spot 范围内用；反模式清单跟正模式清单一样重要（详见 `tool-fit-over-tool-coverage.md`）
- **自主性边界清醒**：在能自动处全自动、在该停处硬停（生产 / 金额 / 跨仓库契约留人工卡点）—— 不是不会全自动，是主动设边界
- **实证主义**：编译过 ≠ 功能可用，看 `git diff` 不看自报（见 `real-e2e-testing.md`）

## 协作风格

- 直接给方案而非列选项让用户选，事后解释决策理由（见 `autonomous-judgment.md`）
- 意图明确时果断执行，不反复确认
- 喜欢用「蜂群/狼群」自然类比表达并行机制（见 `workflow-routing.md` 第二节）

## 不喜欢

- 「弱智」式反复确认（"是否继续？""要不要这样？"）
- 编译/测试通过就声称完成的伪验证
- 过度抽象、为未来不存在的需求设计
- **让用户敲手动命令做 AI 该自主判断的事**（用户原话："我如果都手动，我还要你干嘛"）
- **不必要的耦合（双向）**：全局通用的东西塞进项目，或项目/公司强相关的东西塞进全局
