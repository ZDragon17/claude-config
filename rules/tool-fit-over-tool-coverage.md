引入新工具/框架（liteflow / 规则引擎 / 工作流 / 状态机 / MQ / 流计算等）时，
先列「哪些需求是这个工具的 sweet spot」，哪些不是，**只在 sweet spot 范围内用**。

**Why**：用户原话「不用啥都塞进去，选择合适的需求选择合适的组件是最值得做的一件事」。
工具是手段不是目的，硬塞反而把简单需求做复杂，还污染了工具的语义边界。

**How to apply**：
- 选型评估必须出「✅适配 / ❌不适配 / ⚠️边缘」分类表
- 反模式清单（"不要塞这些进来"）跟正模式清单一样重要
- 首期范围尽量收敛到「业务痛点最真 + 工具语义最匹配」的交集，
  不要"先全量铺开看看"
- 二期由「R1 跑通后真实暴露的下一个痛点」驱动，不是规划期一次性排死
