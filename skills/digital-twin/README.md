# digital-twin

`digital-twin` 是一个面向储能 / IoT / 全栈工程场景的**数字员工 skill**。

它的目标不是复述“作者是谁”，而是把工程实战沉淀为一套可直接用于**技术选型、架构设计、Bug 排查、部署运维、前端工程化、厂商对接**的能力知识库（不绑定任何具体公司或项目）。

## 定位

这个 skill 的核心定位是：

- **技术决策代理**：直接给结论，不回避推荐
- **工程知识库**：把经验按任务类型组织起来
- **风险提醒器**：主动指出边界、陷阱和何时不该这么做

它适合处理的是**技术问题**，不是职业包装、人物设定或通用文案生成。

## 适用场景

适合以下任务：

- 技术选型
- 代码评审
- 架构设计
- Bug 排查
- 部署运维
- 前端工程化
- 厂商 API / 协议对接

尤其适合这些语境：

- 新能源储能
- IoT 设备接入
- 多厂商设备统一抽象
- VPP / EMS / BMS / 云平台
- Java 后端 + Vue / React 前端 + 生产部署

## 不适用场景

以下任务不应该交给这个 skill：

- 简历包装
- 自我介绍优化
- 非技术文案润色
- 与储能 / IoT / 全栈工程无关的泛化建议
- 脱离真实经验边界的空泛趋势讨论

如果要做职业包装或简历整理，请使用独立文档处理，不在本 skill 范围内（本 skill 只沉淀可迁移的工程能力，不做个人材料）。

## 快速开始

### 1. 触发方式

当问题涉及以下主题时，加载 `digital-twin`：

- “这个系统该怎么拆？”
- “这套技术栈该怎么选？”
- “这个 Bug 的根因更可能是什么？”
- “这个部署方案稳不稳？”
- “多品牌设备接入怎么做抽象？”

### 2. 期待输出

正常情况下，这个 skill 应该输出：

1. **结论**
2. **理由**
3. **风险 / 边界**
4. **下一步动作 / 验证方式**

### 3. 一个最小例子

```text
请用 digital-twin 的方式评估：
我们要做一个储能 IoT 平台，支持多厂商接入、调度控制和前端可视化，
应该用什么架构，为什么？
```

更多提问方式和理想回答骨架，见 `examples.md`。

## 使用原则

1. **先技术，后表达**：优先解决问题，不优先讲人设
2. **先结论，后解释**：不要把判断责任甩回给用户
3. **先实战，后趋势**：优先工程实战沉淀，不优先抽象流行说法
4. **先边界，后推荐**：给推荐时必须说清楚什么时候失效
5. **先收敛范围，再扩展知识**：不要让 skill 重新变回“什么都做”的人格包

## 维护方式

维护建议：

- 新的技术默认值变化：更新 `SKILL.md`
- 新的架构经验：更新 `architecture.md`
- 新的部署经验：更新 `deployment.md`
- 新的前端工程经验：更新 `frontend.md`
- 新的事故模式：更新 `lessons.md`
- 新的厂商接入经验：更新 `vendors.md`
- 结构或边界变化：同步更新 `CHANGELOG.md`

## 贡献建议

如果后续继续迭代，建议遵守以下规则：

- 新增内容优先写成**可直接回答问题的知识块**
- 不要只堆项目名、技术栈和做过的事情
- 不要把待确认信息写成事实
- 不要让非技术文档重新混入该目录
