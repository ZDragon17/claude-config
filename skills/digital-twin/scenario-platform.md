# 可复用中台 / 场景化平台设计能力库

本文件是数字员工的**资产运营中台设计能力**：把"每进一个场景就从零做一套采集→告警→工单→报表"，抽象成"**底座建一次、场景包配 N 次**"的可复用平台。

> **能力边界（诚实标注）**：这套方法论目前**扎根在新能源资产运营场景**（储能 / 充电站 / 光伏 / 能源），在该域内已验证可行。下文「9 维最小完备集对任意行业普适」是**设计假设（hypothesis），不是已验证结论**——只在新能源域跑过，跨行业普适性待证。方法论本身（闭环抽象、机制/策略分离、降噪、告警 6 问）作为思考工具可迁移，但迁移到新行业时必须**先用一个垂直切片端到端证明，再泛化**，不要假设它自动成立。

## 一、适用场景

用户需要以下内容时优先用本文件：

- 多个资产/物联运营项目高度同构、想抽公共底座不再每个从零做
- 设计可配置、可多租户、可扩场景的运营中台
- 把"开发交付"转成"配置交付"，并探索机队运维订阅收入
- 评估"该不该抽中台 / 抽到什么粒度"

**不适用**：单一行业一次性交付且无复用预期时，抽中台是过度设计（见风险触发器）。

## 二、核心方法：资产运营闭环

新能源资产运营的本质是同一件事：**让一批资产持续保持在期望状态；一旦偏离，把异常闭环处置掉并沉淀复盘**。

```
采集资产数据 → 判定是否异常 → 定责通知 → 派单处置 → 恢复关闭 → 沉淀报表（→ 复用到下一个场景）
```

冷库温度超标、配电箱过载、电芯热失控、充电桩故障——**业务对象不同，闭环结构一样**。这条闭环是底座的「运行主干」，对场景不变；变的只是"往闭环里填的行业内容"。这是可复用的根据。

> 跨出新能源时：先验证"目标行业的运营也同构于这条闭环"再套用，不要默认。

## 三、9 维最小完备集（推导法）

要把闭环做成"能配置、能复用"，必须回答：**闭环里有哪些可独立配置的环节？** 从"闭环不可省的问题"反推得 5 环节、9 维：

| 闭环环节 | 必答问题 | 配置维度 | 个数 |
|---|---|---|---|
| ① 主体 | 在哪？管什么物理对象？ | 空间 + 资产类型 | 2 |
| ② 观测 | 看什么信号？ | 指标（由资产类型派生） | 1 |
| ③ 判定 | 什么算"一件事"？什么算"一个险"？ | 事件 + 规则 | 2 |
| ④ 响应 | 触发什么动作？谁处置、怎么转办通知？ | 动作 + 工单流程 | 2 |
| ⑤ 沉淀 | 怎么看？怎么算账复盘？ | 看板 + 报表 | 2 |
| | | **合计** | **9** |

**推导逻辑（这才是能力，比记住"9 个"更重要）**：
- **缺一即断裂**：没判定=只是监控大屏不告警；没响应=告警没人管；没沉淀=处置完即遗忘不能复用；没主体/观测=说不清管什么看什么。
- **多一即冗余**：指标拆原始/聚合是实现细节非业务维度；事件+规则合并会丧失"先识别状态变化、再判断成险"的分层降噪；动作+工单合并会丧失"机器自动动作"与"人工处置流程"的分离。
- **正交但有引用级联**：资产类型 _携带_ 指标 → 规则/事件 _依赖_ 指标 → 规则 _触发_ 动作/进入工单。这组依赖保证拼出的场景包**功能自洽**（缺指标的规则进不来）。

> **假设标注**：在新能源域，9 维是这条闭环的最小完备集。对其他行业是否仍"不多不少"——未验证。迁移时重跑这套推导，而不是直接搬 9 维。

## 四、机制 / 策略分离

关键切分：**机制固定在底座、策略可配在场景包**。

| | 归属 | 内容 | 含义 |
|---|---|---|---|
| 机制（不变） | 底座 | 运行主干、降噪、告警/工单状态机、SLA、动作引擎、看板/报表框架、多租户权限 | 一次建设长期复用，质量集中保证 |
| 策略（可变） | 场景包 | 上面 9 维的行业内容（声明式 manifest） | 配置即交付，不写代码扩场景 |

收益：扩新场景=组装场景包而非重写；质量一致（共用验证过的引擎）；规模经济（一套底座服 N 场景）；可做跨客户机队运维订阅；设备无关（架在设备接入层之上，换协议不动业务）。

## 五、运行主干与三层降噪

### 运行主干（事件驱动，阶段间走消息总线解耦）

```
Telemetry → Metric → Event → Alarm → Ticket → Result
设备上报 → 接入层解析 → 适配层订阅标准化 → 属性映射业务指标(单位/口径归一)
  → 更新资产热态(Redis+落库) → 事件中心(识别状态变化) → 匹配规则
  → 生成告警/动作/工单 → 通知人员或联动设备 → 闭环记录 → 报表沉淀
```

### 三层数据分级（防告警泛滥，硬性原则）

| 层 | 含义 | 存储 | 升级条件 |
|---|---|---|---|
| 原始数据 | 设备上报事实 | 时序库 raw hypertable | 默认不升级 |
| 业务事件 | 识别出的状态变化 | 事件中心 | 满足 EventType 识别规则 |
| 告警/工单 | 需人或系统处理的异常 | 告警/工单中心 | 满足规则 + 去抖/分级阈值 |

**降噪四法**（落在事件中心→告警中心之间）：
1. **抖动抑制**：持续 N 时长才成立（如温度 > 8°C 持续 5 分钟）
2. **去重窗口**：相同 (asset, ruleInstance) 在窗口内合并（Redis 滑窗）
3. **聚合收敛**：同空间/同类批量事件聚合为一条父告警
4. **分级**：仅高于阈值的事件升级为告警

## 六、告警闭环与 6 问

状态机：`OPEN → NOTIFIED → ACK/DISPATCHED → PROCESSING →（RECOVER_DETECTED）→ CLOSED`，旁路 `ESCALATED`（超时升级）。

**告警必须可回答的 6 问**（反向约束数据建模——数据模型必须能答出这 6 个，否则闭环不可运营）：

| 问题 | 由哪个字段/机制回答 |
|---|---|
| 谁负责？ | `owner`（按空间/资产责任映射推导） |
| 多久响应？ | `sla.respond` + `acked_at - opened_at` |
| 有没有超时？ | SLA 计时器 + `ESCALATED` |
| 处理了什么？ | `process_log` / 关联工单 |
| 是否恢复？ | `recovered_at`（恢复检测） |
| 同类出现多少次？ | 按 (asset, ruleInstance) 的频次统计 |

## 七、场景包治理

场景包 = 9 维行业内容的**声明式 manifest**，按闭环「主体→观测→判定→响应→沉淀」排列。动作不在包内定义——底座提供原子动作（通知/工单/外部 API/设备指令/改状态/触发策略/写指标），由规则模板引用。

**作者侧保障（缺一即可能配出跑不通的包）**：
- 依赖校验 + 删除保护（缺指标的规则进不来、被引用的不能删）
- 模块契约：声明输入/输出/依赖，组合成 DAG
- **DAG 防环校验** + 缺指标 / 副作用校验
- 沙盒预览：发布前先模拟实例化

**版本升级治理**：发布新版本能识别存量项目 → 生成升级差异 diff → 人工确认 → 保留回滚点。

**反模式**：把行业逻辑硬编码进底座；场景包里写死租户数据；规则直接读写别的中心库表（应只走领域事件 + 动作编排出口）。

## 八、与设备接入平台的契约

中台**架在设备接入平台之上（如 JetLinks）、设备无关**，复用既有接入能力。

```
接入平台创建设备/产品/物模型
  → 中台同步产品与设备（订阅变更事件做增量同步 + 低频定时对账兜底）
  → 绑定业务资产 → 映射设备属性到业务指标 → 设置单位/阈值/展示 → 进入运行态
```

**同步策略**：优先订阅增量，辅以定时对账修复漏接；映射关系（产品↔资产类型、属性↔指标、device↔asset）持久化在中台侧，**不反向写接入平台**。这是"双系统数据一致"的通用模式——增量为主、对账兜底。

## 九、跨租户机队总控

同一套闭环引擎，**两个视角看同一组告警/工单**——因为所有告警/工单**形状一致**，才可能做跨客户聚合：

| 视角 | 是谁 | 范围 | 本质 |
|---|---|---|---|
| 应用场景运营 | 客户管理员/成员 | 本租户、受数据域约束 | 客户自己的运维中心 |
| 服务商运维总控 | 服务商 | 跨租户聚合 | 按客户/资产/告警量计运维订阅费 |

把一次性交付变成经常性收入（ARR）的结构性根据：**形状统一 → 可聚合 → 可订阅**。

## 十、关键技术决策

> 默认值取自数字人既有选型 DNA（见 SKILL.md 第五节），此处只列本场景的针对性结论与"何时打破"。

| 决策 | 结论 | 理由 | 何时打破 |
|---|---|---|---|
| 元数据驱动 | **是**：9 维由场景包声明式定义、运行时解释执行 | "扩行业不重开发"成立的前提 | 极高频热路径字段可固化为强类型列 |
| 规则引擎 | **Drools（复杂业务规则）+ 轻量表达式（Aviator/SpEL，阈值热路径）混合** | Drools 适合可调复杂规则；简单阈值用表达式免会话开销 | 规则极简全表达式；极复杂全 Drools |
| 指标计算 | **流式实时（热路径）+ 定时聚合（报表口径）双轨** | 告警要实时；报表批算更稳更省 | 纯展示类全定时 |
| 主存储 | **PostgreSQL + TimescaleDB 单引擎** | 同时需要时序 + 重度 JSONB（元数据驱动），正命中 PG 的适用条件（见 SKILL.md 第七节 MySQL→PG 打破条件），单引擎省运维 | 团队强依赖 MySQL 时 MySQL + TimescaleDB 双库 |
| 事件总线 | **RabbitMQ** | 管线解耦、死信做重试、路由做告警分发、运维简单 | 日消息 > 千万级或需回溯上 Kafka |
| 认证授权 | **Sa-Token + 数据域拦截器** | 多租户 + RBAC + 行级数据域 | 需作 OAuth2 Server 时换 Security |
| 运行形态 | **Spring Boot 3 单体模块化（Undertow），中心=模块、事件解耦** | 中小团队成本最低 | 团队 > 10 人 / 独立发布 / 独立扩缩容时拆服务 |

**横切约束**：跨域用领域事件解耦；一致性用幂等键 + 乐观重试；外部依赖必有 fallback；密码只走环境变量（12-Factor）。

**AI 预留（生成不直改运行态）**：AI 适合场景包作者侧/运营分析侧——生成 manifest 草稿、建议规则参数、解释升级差异、复盘报表。但**只生成草稿与建议，必过 schema 校验 + 沙盒 + 发布审批**，不允许绕过契约/数据域/审批直改运行态规则。

## 十一、风险触发器

遇到以下情况必须主动提醒：

1. **抽象过早/过度**：还没一个垂直切片端到端跑通，就想一次抽象覆盖所有行业 → 先 P0 切片证明再泛化
2. **跨行业直接套 9 维**：把新能源验证过的 9 维当成新行业的既定结论 → 重跑闭环推导
3. **机制/策略边界泄漏**：行业逻辑硬编码进底座，或底座知道具体场景细节
4. 设备接入耦合：中台反向写接入平台 / 业务层直接依赖设备协议
5. 只设计主链路：不设计降噪、SLA、死信、对账兜底
6. 单一行业一次性交付还要抽中台 = 过度设计
