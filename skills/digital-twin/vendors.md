## 一、适用场景

当用户需要以下内容时，优先使用本文件：

- 新厂商 API 接入
- 多品牌统一抽象设计
- 认证方式选择与凭证管理
- 配置下发、限流、fallback 设计
- 澳洲 VPP / AEMO 相关集成

## 二、默认对接立场

### 1. 默认原则

- **统一抽象优先**：调度层只认抽象指令，不认品牌细节
- **配置读取优先**：写配置前先读取现有配置
- **凭证外部化**：密钥只走环境变量，不写死
- **限流与容错是标配**：厂商 API 默认不稳定、不高 SLA
- **标准化在 Converter 层完成**，不要把各品牌字段散落到业务层

### 2. 默认回答方式

输出厂商对接方案时，必须明确：

1. 认证方式
2. 执行器 / 适配器抽象怎么落
3. 下发参数如何防覆盖
4. 如何做限流、重试、fallback
5. 数据字段、单位、精度如何标准化

## 三、输出对接方案时的固定结构

1. **结论**：推荐的接入方式与抽象层设计
2. **认证与凭证**：如何认证、凭证放哪里
3. **执行链路**：抽象指令 → 执行器 → 厂商 API
4. **配置与数据处理**：GET-合并-PUT、Converter 标准化
5. **风险**：覆盖语义、限流、第三方 SLA、环境差异
6. **验证**：联调时先验证哪些点

## 五、标准对接流程

### 1. Actuator 抽象

```text
1. 继承 AbstractActuator
2. 实现品牌协议转换（抽象指令 → 品牌 API 参数）
3. 注册到 ActuatorFactory
4. 调度层按品牌选择 Actuator，无需知道具体协议
```

### 2. 必须做的事

- **配置下发前先读取**：永远先 GET 当前配置，合并后再写入
- **API 容错**：主 API + fallback URL 双通道
- **认证信息外部化**：API Key / Secret 通过环境变量注入
- **速率控制**：厂商 API 通常有 QPS 限制，用 Resilience4j 限流

### 3. 联调优先顺序

1. 先确认认证是否稳定可复用
2. 再确认读接口的字段、单位、精度
3. 再确认写接口是 PATCH 还是全量覆盖语义
4. 最后确认异常码、限流、超时和 fallback

## 六、数据标准化规则

- 各家 API 返回的字段名、单位、精度不同
- 在 `Converter` 层统一转换为内部数据模型
- 单位换算在 `Converter` 完成（如 W → kW，0.1V → V）
- 不允许把品牌私有字段直接扩散到上层业务逻辑

## 七、澳洲市场对接能力

### 1. AEMO 电价 API

- 特点：AEMO 提供公共电价 / 需求 API，无认证，但 SLA 不稳定
- 能力要点：必须做**主备双通道**（主 dashboard 域 + 备 visualisations 域），主失败自动切备；具体 endpoint 以 AEMO 当期文档为准（会变更，不硬编码）

### 2. VPP 调度流程

```text
AEMO 电价信号
  → Optimization 策略引擎（SoC 感知 + 电价阈值）
    → DR Dispatcher（抽象指令）
      → 品牌 Actuator（协议转换）
        → 厂商 API（实际下发）
          → 设备执行
```

### 3. 套利策略

- 保守：仅在电价差 > 阈值时操作
- 平衡：标准峰谷套利
- 激进：最大化收益，接受更高风险
- 电池容量需在「用户自用」与「VPP 调度」间按策略分配，比例随商业模式可配（不是固定值）

## 八、风险触发器

遇到以下情况时，必须主动提醒风险：

1. 用户默认把厂商写接口当 PATCH 用
2. 调度层直接拼接品牌参数，没有抽象层
3. 密钥硬编码在代码或配置默认值里
4. 多品牌数据直接在业务层做 if-else 单位换算
5. 外部公共 API 没有 fallback
6. 澳洲和国内域名 / 区域环境混用
