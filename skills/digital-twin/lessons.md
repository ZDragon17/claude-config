# 失败模式与排障能力库

本文件是数字员工的**排障能力沉淀**：在 Bug 排查、事故复盘、根因定位时，凭这套失败模式识别能力直接锁定方向。记录的是**可复用的失败模式 + 真实现场信号 + 解法**，不是抽象调试口号，也不绑定任何具体项目。

> 协议层规约（Modbus/MQTT/RS485/设备状态机）的**正确做法**沉淀在全局规则 `modbus-protocol` / `mqtt-iot` / `iot-device` 中。本文件不复述规约，只提供**这些规约被违反时长什么样、怎么抓现场、如何确认修复**——把规约从"该怎么做"补全为"做错了怎么认出来"。

## 一、使用原则

### 1. 默认排障顺序

1. **抓现场**：抓包、日志、JFR、原始请求 / 响应，不猜
2. **看信号**：从"现象模式"反推根因候选
3. **修根因**：优先修协议边界、并发冲突、状态机问题
4. **做验证**：测试或手动验证步骤必须补齐
5. **沉淀模式**：把新模式写回本能力库

### 2. 适用场景

- MQTT / Modbus / RS485 / 厂商 API 相关故障
- 虚拟线程、并发、超时、假死问题
- 实时数据错乱、闪烁、串流问题
- 配置下发覆盖、状态机异常、外部 API 不稳定问题

## 二、排障输出模板

排障问题默认按以下结构输出：

1. **现象**：用户看到的异常是什么
2. **最可能根因**：优先级最高的 1~3 个候选
3. **先抓什么现场**：日志、抓包、JFR、数据库状态、消息轨迹
4. **修复建议**：修根因，不修表象
5. **验证方式**：怎么确认真的修好了

## 三、高频异常信号速查

| 异常信号 | 优先怀疑方向 |
|---|---|
| 批量任务超时，但 CPU 不高、线程数正常 | 虚拟线程 Pin / 公共线程池阻塞 |
| 设备状态正常却持续报虚假故障 | 协议边界解析错误 / CRC 被当数据 |
| 历史数据间歇性读不到 | RS485 半双工总线争用 |
| 前端数据闪烁、交替、忽有忽无 | 多通道数据互串 / 主题路由错误 |
| 某个离线事件只记录一次，后续都丢失 | 状态机旧记录未关闭 |
| 改 A 配置导致 B 配置丢失 | 厂商 API 是全量覆盖语义 |
| 第三方数据偶尔为空 | 外部 API 不稳定，缺少 fallback |

## 四、失败模式库

> 每条 = 现场信号 + 根因 + 解法 + 验证。前四条印证全局协议规约的失败侧（规约本身见对应全局规则），后三条是规约未覆盖的独立能力。

### 1. 虚拟线程 Pin 阻塞（Java 21 虚拟线程场景）

- **现场信号**：周期性系统假死，批量任务全部超时（"完成:0/N"），但 CPU 不高、线程数正常
- **根因**：`parallelStream()` 走 `ForkJoinPool.commonPool`，虚拟线程被 Pin 在 Carrier 线程上，任务全部排队
- **解法**：禁用 `parallelStream` 改顺序流；禁用 HTTP/2（OkHttp 内部 `synchronized` 同样会 Pin）
- **验证**：`-Djdk.tracePinnedThreads=short` + JFR 持续录制
- **能力要点**：Java 21 虚拟线程三大禁区 —— `synchronized`、`parallelStream`、HTTP/2 客户端

### 2. Modbus 帧尾校验码误解析为业务数据（Modbus 设备接入场景）

- **印证规约**：`modbus-protocol`「校验码被误当数据」「声明长度可能与实际不一致，以实际载荷为准」
- **现场信号**：健康设备（SOC/SOH 正常）持续报固定几个虚假故障，故障码是个固定怪值
- **根因**：帧声明长度 > 实际载荷，按声明长度取数把帧尾 2 字节 CRC 当成了业务字段
- **解法**：声明长度 > 可用长度时，从可用长度扣掉 2 字节 CRC 再解析
- **验证**：实时抓包确认原始帧十六进制
- **能力要点**：设备看起来健康却持续报故障 → 第一反应查帧解析边界

### 3. RS485 半双工总线争用（多指令源设备接入场景）

- **印证规约**：`modbus-protocol`「多指令必须排队串行」「批量读取期间暂停定时采集」
- **现场信号**：历史数据时有时无，无固定规律，设备本身正常
- **根因**：定时采集指令与批量读取指令在半双工总线上争用
- **解法**：批量读取期间暂停定时采集，调度层互斥，不靠底层队列侥幸
- **能力要点**：间歇性失败 + 设备正常 → 先看总线争用

### 4. 多通道数据互串导致告警闪烁（MQTT 多主题接入场景）

- **印证规约**：`mqtt-iot`「不同通道数据不能互串」「不认识的帧直接丢弃」
- **现场信号**：告警状态频繁闪烁（有 → 无 → 有循环）
- **根因**：某通道的帧被错误路由到另一处理器，与正常通道数据交替推送
- **解法**：处理器只认自己的帧类型，不认识的直接丢弃，不"顺便"路由
- **能力要点**：前端状态来回跳 → 查通道隔离与主题路由

### 5. 设备离线记录僵尸化（设备状态机场景）

- **印证规约**：`iot-device`「旧的未关闭离线记录必须先关闭，再创建新记录」
- **现场信号**：离线事件只记录一次，后续所有离线事件丢失
- **根因**：创建新记录前检查"是否存在未关闭记录"，旧记录长期未关闭，新事件永远被阻塞
- **解法**：创建前先关闭所有未关闭旧记录——"先清理再创建" > "检查后拒绝"
- **能力要点**：某事件只出现一次就沉默 → 查旧状态残留

### 6. 配置下发覆盖已有设置（厂商配置接口场景）

- **现场信号**：下发新参数后，已有的另一组参数被清空（改 A 丢 B）
- **根因**：补丁下发前未合并已有配置，而厂商接口实际是全量覆盖（PUT）语义
- **解法**：下发前先 GET 当前配置，与新参数合并后再写入
- **能力要点**：默认按"全量覆盖"防御，不默认相信 PATCH 语义

### 7. 外部公共 API 不稳定（第三方数据集成场景）

- **现场信号**：依赖的第三方数据偶尔为空
- **根因**：外部公共 API 无 SLA 保障，间歇性不可用
- **解法**：主备双通道，主 API 失败自动切 fallback URL
- **能力要点**：第三方数据间歇缺失 → 优先查 SLA 与 fallback 设计

## 五、常见反模式

以下排障方式一律警惕：

1. 没抓现场就凭经验拍脑袋
2. 过滤异常值代替修协议根因
3. 在并发 / 虚拟线程问题上只看 CPU，不看线程与 JFR
4. 出现串流问题时还尝试"兼容性路由"
5. 修完不验证，导致事故回归
