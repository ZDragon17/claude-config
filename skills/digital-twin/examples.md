# examples

本文件用于展示 `digital-twin` 的典型提问方式，以及它理想中的回答骨架。

这些示例不是标准答案模板，而是帮助使用者理解：

- 什么问题适合交给这个 skill
- 这个 skill 应该怎样组织回答
- 它会如何给结论、讲理由、提风险、给下一步

## 使用说明

阅读这些示例时，重点看三件事：

1. **提问是否具体**：问题越接近真实工程任务，回答越有价值
2. **回答是否先给结论**：`digital-twin` 不应该先铺垫一大段背景
3. **是否明确边界与风险**：推荐之外，必须说明什么时候不该这么做

## 示例 1：技术选型

### 用户提问

```text
我们准备做一个储能 IoT 平台，后端要接多厂商设备，前端要做管理后台和实时监控，
现在技术栈还没定。请用 digital-twin 的方式给推荐。
```

### 理想回答骨架

1. **结论**：推荐 Java 17 / Spring Boot 3.x / Undertow / MyBatis-Plus 或 MyBatis-Flex / Redis + Redisson / RabbitMQ / Vue 3 + Element Plus
2. **理由**：
   - LTS 稳定，适合生产
   - 多厂商接入、IoT 高并发、规则配置、中文生态都更匹配
   - 管理后台用 Vue 成本更低
3. **不推荐**：
   - 不建议一上来就上 Spring Cloud 全家桶
   - 不建议优先用 JPA / Hibernate
4. **风险 / 边界**：
   - 需要 OAuth2 Server 时再考虑打破 Sa-Token 默认值
   - 日消息量上千万级再考虑 Kafka
5. **下一步**：
   - 先确认团队规模、发布节奏、是否需要时序库、是否有桌面端需求

## 示例 2：代码评审

### 用户提问

```text
你帮我看一下这个储能平台的后端代码结构合不合理，重点看分层、异常处理和配置管理。
```

### 理想回答骨架

1. **结论**：这份代码整体是否符合模块化单体思路，哪里偏了
2. **问题点**：
   - `controller` 是否写了业务逻辑
   - 异常是否统一走 `PlatformException` + `ErrorCode`
   - 密码 / 密钥是否只走环境变量
3. **影响**：
   - 分层混乱会让协议接入和业务规则耦死
   - 异常不统一会让前端和日志难以对齐
4. **修改建议**：
   - 业务逻辑下沉到 `service`
   - 补全全局异常处理
   - 清理默认敏感配置
5. **是否违背既有风格**：明确指出是否偏离 `com.example.xxx` 分层结构偏好

## 示例 3：架构设计

### 用户提问

```text
我们要支持 6 家储能厂商接入，还要做调度、结算和前端聚合 API，
这套系统该怎么拆模块比较稳？
```

### 理想回答骨架

1. **结论**：推荐单体模块化 + 业务域拆分，而不是先微服务
2. **模块划分**：
   - IoT Hub
   - Optimization
   - DR Dispatcher
   - Market & Billing
   - BFF
   - Identity
   - Open API
   - Admin Control
3. **关键模式**：
   - Actuator 抽象
   - 协议适配器层
   - 事件驱动解耦
   - 幂等键 + 乐观重试
4. **风险 / 边界**：
   - 调度层不应知道品牌细节
   - 只做主链路、不做缓存与降级是高风险
5. **下一步**：
   - 先画模块边界和数据流，再决定是否需要单独拆 BFF / Open API

## 示例 4：Bug 排查

### 用户提问

```text
系统每隔几个小时就会批量超时，但 CPU 不高，线程数看起来也正常。
你觉得最该先查什么？
```

### 理想回答骨架

1. **现象判断**：这是典型“看起来不忙但任务卡死”的问题
2. **最可能根因**：
   - 虚拟线程 Pin
   - `parallelStream()` 抢占公共线程池
   - HTTP/2 客户端内部锁竞争
3. **先抓什么现场**：
   - JFR
   - `-Djdk.tracePinnedThreads=short`
   - 批量任务超时日志
4. **修复建议**：
   - 禁用 `parallelStream`
   - 避免在虚拟线程路径上使用大面积 `synchronized`
5. **验证方式**：
   - 连续压测 / 长时间运行，看批量任务是否仍出现 `完成:0/N`

## 示例 5：部署运维

### 用户提问

```text
这个平台要上澳洲生产环境，你会怎么做主备和故障切换？
```

### 理想回答骨架

1. **结论**：推荐 ALB + 主备双机 + Nginx + Redis Sentinel + 探活脚本
2. **拓扑**：
   - Master 节点承载应用、数据库、Redis、前端容器
   - Backup 节点镜像部署接管故障
3. **关键配置**：
   - `/actuator/health`
   - `/nginx-health`
   - 故障 3 次失败判定、恢复 5 次成功判定
   - Redis 分布式锁防脑裂
4. **风险**：
   - 只有主备，没有真实切换演练
   - 没有 `start_period` 导致 Java 容器误判失败
5. **下一步**：
   - 演练切换、核查告警、确认日志分层

## 示例 6：前端工程化

### 用户提问

```text
我们要做一个储能管理后台，既要设备列表和配置，也要实时 MQTT 数据展示。
前端你建议怎么搞？
```

### 理想回答骨架

1. **结论**：推荐 Vue 3 + Element Plus + Pinia + Vite + TypeScript 严格模式
2. **理由**：
   - 管理后台组件成熟
   - 中文生态好
   - 团队上手成本低
3. **实时链路**：
   - MQTT 连接统一管理
   - 使用引用计数模式维护订阅
   - 自动重连 + 随机 clientId
4. **风险 / 边界**：
   - 不要让每个组件各自创建 MQTT 连接
   - 如果需要桌面端，再考虑 React + Electron
5. **下一步**：
   - 先确定页面类型：后台 / 大屏 / 桌面端，再决定是否拆前端形态

## 示例 7：厂商对接

### 用户提问

```text
FoxESS 和 Growatt 都要接进来，调度层不想感知品牌细节，应该怎么设计？
```

### 理想回答骨架

1. **结论**：用 `AbstractActuator` + `ActuatorFactory` 做统一执行器抽象
2. **执行链路**：
   - 抽象指令
   - 品牌 Actuator
   - 厂商 API
3. **关键规则**：
   - 配置写入前先 GET 当前配置
   - 合并后再 PUT
   - 认证信息全部外部化
4. **风险 / 边界**：
   - FoxESS 配置下发默认按全量覆盖语义防御
   - Growatt 注意澳洲与国内域名差异
5. **验证方式**：
   - 先联调读接口，再联调写接口，再测 fallback、限流和异常码

## 示例 8：边界提醒

### 用户提问

```text
你帮我用 digital-twin 写一版大厂后端求职自我介绍。
```

### 理想回答骨架

1. **边界说明**：这不属于 `digital-twin` 的技术决策范围
2. **原因**：该 skill 已经收敛为纯技术知识库，不再承担职业包装任务
3. **引导**：
   - 如需整理职业材料，请用独立文档处理，不在本 skill 范围内
4. **不要做的事**：
   - 不要硬把这个 skill 扩展成非技术包装器
